Módulo 3 — Scripting y Control de Acceso

Introducción: automatizar la defensa

En ciberseguridad, la automatización no es opcional. Cuando respondes a un incidente, no tienes tiempo de ejecutar 50 comandos manualmente. Necesitas scripts que recopilen evidencia, verifiquen integridad y apliquen controles en segundos.

Este módulo cubre dos pilares fundamentales: 1. Scripting en Bash — automatizar tareas de seguridad 2. Control de Acceso — gestionar quién puede hacer qué en el sistema

El flujo de trabajo de Git

    ┌─────────────────────────────────────────────────────────────┐
    │                 FLUJO DE TRABAJO GIT                        │
    │                                                             │
    │   ┌──────────────┐                                          │
    │   │  WORKING     │  ← Tu directorio de trabajo actual      │
    │   │  DIRECTORY   │     (archivos que editas)               │
    │   └──────┬───────┘                                          │
    │          │ git add                                          │
    │          ▼                                                  │
    │   ┌──────────────┐                                          │
    │   │  STAGING     │  ← Área de preparación                  │
    │   │  AREA        │     (archivos listos para commit)       │
    │   └──────┬───────┘                                          │
    │          │ git commit                                       │
    │          ▼                                                  │
    │   ┌──────────────┐                                          │
    │   │  LOCAL       │  ← Tu repositorio local                 │
    │   │  REPO        │     (historial completo en tu máquina)  │
    │   └──────┬───────┘                                          │
    │          │ git push / git pull                              │
    │          ▼                                                  │
    │   ┌──────────────┐                                          │
    │   │  REMOTE      │  ← Repositorio remoto (GitHub, GitLab)  │
    │   │  REPO        │     (compartido con el equipo)          │
    │   └──────────────┘                                          │
    │                                                             │
    └─────────────────────────────────────────────────────────────┘

Commit: snapshot, no diferencia

Un commit es una “foto” completa de tus archivos en un momento específico. No es una diferencia (diff) — es el estado completo del proyecto en ese instante.

    ┌──────────────────────────────────────────────────────┐
    │                 HISTORIAL DE COMMITS                 │
    │                                                      │
    │   commit a1b2c3  ← "Agregar script de análisis"      │
    │        │                                             │
    │        ▼                                             │
    │   commit d4e5f6  ← "Corregir bug en parser"          │
    │        │                                             │
    │        ▼                                             │
    │   commit g7h8i9  ← "Documentar hallazgos"           │
    │                                                      │
    │   Cada commit tiene:                                 │
    │   - Hash único (a1b2c3...)                          │
    │   - Mensaje descriptivo                              │
    │   - Autor y timestamp                                │
    │   - Referencia al commit anterior                    │
    │                                                      │
    └──────────────────────────────────────────────────────┘

Push / Pull: sincronización remota

  • Push: envía tus commits locales al repositorio remoto
  • Pull: trae los cambios del remoto a tu máquina local

Comandos esenciales con ejemplos

git init — crear un repositorio

# Crear un directorio para el proyecto
mkdir laboratorio-seguridad
cd laboratorio-seguridad

# Inicializar repositorio Git
git init
Initialized empty Git repository in /home/estudiante/laboratorio-seguridad/.git/

git clone — clonar un repositorio existente

# Clonar un repositorio remoto
git clone https://github.com/usuario/repo-seguridad.git
Cloning into 'repo-seguridad'...
remote: Enumerating objects: 42, done.
Receiving objects: 100% (42/42), done.

git add y git status — preparar cambios

# Verificar el estado actual
git status
On branch main
Untracked files:
  (use "git add <file>..." to include in commit)
        script_analisis.sh

nothing added to commit but untracked files present
# Agregar un archivo específico al staging area
git add script_analisis.sh

# Agregar todos los cambios
git add .

git commit — guardar snapshot

# Crear commit con mensaje descriptivo
git commit -m "Agregar script de análisis de logs"
[main a1b2c3d] Agregar script de análisis de logs

Advertencia: Los mensajes de commit deben ser descriptivos. git commit -m "cambios" no dice nada. git commit -m "Agregar parser para logs de autenticación" sí.

.gitignore correcto

Qué ignorar

El archivo .gitignore le dice a Git qué archivos NO debe versionar. En ciberseguridad, esto es crítico.

# ═══════════════════════════════════════════════════
# .gitignore para proyectos de ciberseguridad
# ═══════════════════════════════════════════════════

# CREDENALLES - NUNCA versionar
*.pem
*.key
*.p12
*.pfx
.env
.env.*
secrets/
credentials/
passwords.txt
*.secret

# ARCHIVOS TEMPORALES
*.tmp
*.log
*.bak
*~
.DS_Store
Thumbs.db

# OUTPUTS DE HERRAMIENTAS
nmap_output/
scan_reports/
pcap_captures/*.pcap
evidence/screenshots/

# ARCHIVOS GRANDES
*.iso
*.img
*.zip
*.tar.gz

# ENTORNOS VIRTUALES
venv/
.venv/
node_modules/

Qué NO ignorar

Archivo Por qué versionarlo
Scripts (.sh, .py) Son el trabajo principal
Documentación (.md) Explica el propósito y uso
Plantillas (.template) Base para configuraciones
Archivos de configuración Permiten reproducir el entorno

Advertencia de seguridad: Si alguna vez commiteas credenciales por accidente, cambiar la contraseña inmediatamente. Eliminar el archivo de Git no basta — el historial conserva el commit. Usa git filter-branch o BFG Repo-Cleaner para eliminar datos sensibles del historial.

Estrategia de ramas: Git Flow simplificado

En este curso seguimos la convención definida en CONTRIBUTING.md: una estructura de tres niveles que separa el desarrollo de las correcciones de estabilidad.

    ┌────────────────────────────────────────────────────────────────────┐
    │                    ESTRATEGIA DE RAMAS (CONTRIBUTING.md)          │
    │                                                                    │
    │   main   ──────●────────────────────●──────────────────●──────►     │
    │              │                    │                    │             │
    │              │        merge       │                    │             │
    │              └────── develop ─────┘                    │             │
    │                      │                                    │             │
    │                      │                    merge         │             │
    │                      │    ┌──── fix/corregir-timeout ────┘             │
    │                      │    │                                        │
    │                      ▼    ▼                                        │
    │                    feature/                                      │
    │                    nmap-escaneo                                    │
    │                    │                                               │
    │             ┌──────●───●───●───●───●─┐                           │
    │             │  commits atómicos con  │                            │
    │             │  Conventional Commits │                            │
    │             └────────────────────────┘                           │
    │                                                                    │
    │   • main:     código de producción estable                          │
    │   • develop:  integración de nuevas funcionalidades                 │
    │   • feature/*: desarrollo de una funcionalidad concreta            │
    │   • fix/*:    correcciones rápidas desde main (hotfixes)            │
    │                                                                    │
    └────────────────────────────────────────────────────────────────────┘

Convenciones de ramas

Tipo de rama Prefijo Creado desde Uso
main — — Código estable, listo para producción
develop — main Integración de features antes de merge a main
Feature feature/ develop Nueva funcionalidad (ej: feature/nmap-escaneo)
Fix fix/ main Corrección urgente de producción (ej: fix/corregir-timeout)

Conventional Commits

Los mensajes de commit siguen el formato Conventional Commits:

Tipo Uso Ejemplo
feat: Nueva funcionalidad feat: agregar parser para logs de autenticación
fix: Corrección de bug fix: corregir regex que fallaba con timestamps
docs: Cambios en documentación docs: actualizar guía de uso de tcpdump
refactor: Reestructuración sin cambios de comportamiento refactor: simplificar lógica de validación 
# ✅ BIEN: commits atómicos con tipo convencional
git commit -m "feat: agregar script de descubrimiento de hosts"
git commit -m "fix: corregir filtro tcpdump para tráfico DNS"
git commit -m "docs: documentar filtros avanzados de tcpdump"

# ❌ MAL: commit monolítico sin tipo
git commit -m "cambios"

Nota del instructor: Cada commit debe ser una “foto” verificable. Si no puedes describir en una línea lo que cambió, el commit es demasiado grande. feat: y fix: no son solo estilo — son contratos con tu equipo y con el futuro tú.

Commits atómicos

Un commit atómico contiene un solo cambio lógico. No mezcles correcciones de bugs con nuevas funcionalidades. Si un commit incluye “agregar funcionalidad” y “corregir bug”, tu git bisect se vuelve inútil para localizar cuándo se introdujo el error.

# ❌ MAL: un commit con múltiples cambios no relacionados
git commit -m "Varios cambios y correcciones"

# ✅ BIEN: commits separados por cambio lógico
git commit -m "feat: agregar parser para logs de autenticación"
git commit -m "fix: corregir regex que fallaba con timestamps"
git commit -m "docs: documentar uso del script de análisis"

Minipasos guiados

Paso 1: Crear repositorio local

mkdir lab-seguridad
cd lab-seguridad
git init

# Configurar identidad (solo una vez por máquina)
git config --global user.name "Tu Nombre"
git config --global user.email "tu@email.com"

Paso 2: Primer commit con notas de laboratorio

# Crear archivo de notas
cat > notas_laboratorio.md << 'EOF'
# Notas de Laboratorio

## Fecha: 2024-01-15
## Objetivo: Análisis de logs de autenticación

### Hallazgos
- 47 intentos de acceso fallidos desde IP 192.168.1.100
- 2 accesos exitosos fuera de horario laboral

### Próximos pasos
- Investigar IP sospechosa
- Revisar logs de los últimos 7 días
EOF

# Agregar y commitear
git add notas_laboratorio.md
git commit -m "Agregar notas iniciales de laboratorio"

Paso 3: Push a repositorio remoto

# Agregar repositorio remoto
git remote add origin https://github.com/tu-usuario/lab-seguridad.git

# Enviar commits
git push -u origin main

Paso 4: Clonar en otra máquina

# En otra máquina, clonar el repositorio
git clone https://github.com/tu-usuario/lab-seguridad.git
cd lab-seguridad

# Verificar el historial
git log --oneline

Notas de seguridad: nunca commitees credenciales

El error más común (y más peligroso)

# ❌ NUNCA hagas esto
echo "password123" > config.env
git add config.env
git commit -m "Agregar configuración"
git push

Si subes credenciales a un repositorio público:

  1. Cualquiera puede verlas — bots escanean GitHub 24/7 buscando secretos
  2. El historial persiste — borrar el archivo no lo elimina del historial
  3. El daño es inmediato — atacantes automatizados explotan credenciales en minutos

Prevención

# 1. Crear .gitignore ANTES de empezar
echo "*.env" >> .gitignore
echo "credentials/" >> .gitignore

# 2. Usar variables de entorno
export DB_PASSWORD="secreto"
# En el código: os.environ['DB_PASSWORD']

# 3. Usar herramientas de detección
# git-secrets, trufflehog, gitleaks

Advertencia de seguridad: Si accidentalmente commiteas una contraseña, cámbiala INMEDIATEMENTE. No basta con hacer otro commit que elimine el archivo — el secreto sigue en el historial de Git.

Scripting en Bash para ciberseguridad

¿Por qué script en seguridad?

Los scripts automatizan tareas repetitivas: recopilar evidencia, verificar hashes, escanear puertos, generar reportes. En respuesta a incidentes, un script puede hacer en segundos lo que a un humano le tomaría horas.

Estructura básica de un script

#!/bin/bash
# Script: verificar-integridad.sh
# Propósito: Verificar integridad de archivos críticos del sistema

# Variables
DIRECTORIO="/etc"
ARCHIVO_HASH="hashes_criticos.sha256"

# Verificar si el archivo de hashes existe
if [ ! -f "$ARCHIVO_HASH" ]; then
    echo "ERROR: Archivo de hashes no encontrado"
    exit 1
fi

# Verificar integridad
cd "$DIRECTORIO"
sha256sum -c "$ARCHIVO_HASH" 2>/dev/null

if [ $? -eq 0 ]; then
    echo "✅ Integridad verificada: ningún archivo modificado"
else
    echo "❌ ALERTA: Archivos modificados detectados"
    echo "Ejecutar: auditctl -w $DIRECTORIO -p wa -k integrity_check"
    exit 1
fi

Scripting para recolección de evidencia

#!/bin/bash
# Script: recolectar-evidencias.sh
# Uso: bash recolectar-evidencias.sh

FECHA=$(date +%Y%m%d_%H%M%S)
DIR_EVIDENCIA="~/laboratorio/evidencias/$FECHA"

mkdir -p "$DIR_EVIDENCIA"

# 1. Listar procesos activos
ps aux > "$DIR_EVIDENCIA/procesos.txt"

# 2. Conexiones de red
ss -tulnp > "$DIR_EVIDENCIA/conexiones.txt"

# 3. Logs de autenticación
sudo cp /var/log/auth.log "$DIR_EVIDENCIA/auth.log" 2>/dev/null

# 4. Usuarios con privilegios
awk -F: '$3 == 0 {print $1}' /etc/passwd > "$DIR_EVIDENCIA/root_users.txt"

echo "Evidencias recolectadas en: $DIR_EVIDENCIA"

Automatización con cron

# Ejecutar verificación de integridad cada hora
0 * * * * /home/estudiante/scripts/verificar-integridad.sh >> /var/log/integridad.log 2>&1

# Backup diario a las 2:00 AM
0 2 * * * /home/estudiante/scripts/backup-diario.sh

Control de Acceso: sudoers y PAM

El archivo sudoers

Controla quién puede ejecutar qué como root:

# Formato: usuario HOST=(runas) COMANDOS
ops_admin ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx
dev_user ALL=(ALL) NOPASSWD: /usr/bin/docker
auditor ALL=(ALL) NOPASSWD: /usr/bin/journalctl

Buenas prácticas

Práctica Razón
NOPASSWD solo para comandos específicos No dar shell root completo
Grupos en vez de usuarios individuales Escalable
Alias para conjuntos de comandos Mantenible
visudo para editar Validación de sintaxis 
# Usar visudo (nunca editar directamente)
sudo visudo

# Ejemplo con alias
Cmnd_Alias WEB_CMDS = /usr/bin/systemctl restart nginx, /usr/bin/systemctl reload nginx
ops_admin ALL=(ALL) NOPASSWD: WEB_CMDS

PAM: autenticación modular

PAM permite configurar autenticación por servicio:

# /etc/pam.d/sshd
auth required pam_google_authenticator.so
account required pam_nologin.so
password requisite pam_pwquality.so retry=3

Políticas de contraseñas

# /etc/login.defs
PASS_MAX_DAYS 90      # Expiración de contraseña
PASS_MIN_DAYS 1       # Mínimo entre cambios
PASS_WARN_AGE 14      # Advertencia antes de expirar

3.1 🎯 Ejercicio práctico: script de auditoría + sudoers

Objetivo: Crear script de recolección de evidencias y configurar sudoers limitado.

Parte A: Script de auditoría

  1. Crear directorio:

    mkdir -p ~/laboratorio/scripts

  2. Crear script recolectar-evidencias.sh:

    cat > ~/laboratorio/scripts/recolectar-evidencias.sh << 'EOF'
#!/bin/bash
DIR="$HOME/laboratorio/evidencias/$(date +%Y%m%d_%H%M%S)"
mkdir -p "$DIR"
ps aux > "$DIR/procesos.txt"
ss -tulnp > "$DIR/conexiones.txt"
echo "Evidencias en: $DIR"
EOF
chmod +x ~/laboratorio/scripts/recolectar-evidencias.sh

  3. Ejecutar y verificar:

    bash ~/laboratorio/scripts/recolectar-evidencias.sh
ls ~/laboratorio/evidencias/*/

Parte B: sudoers limitado

  1. Crear archivo sudoers:

    echo "estudiante ALL=(ALL) NOPASSWD: /usr/bin/systemctl status sshd" | sudo tee /etc/sudoers.d/estudiante
sudo chmod 440 /etc/sudoers.d/estudiante

  2. Verificar:

    sudo -l

Validación:

Prueba Comando Esperado
Script ejecutable bash ~/laboratorio/scripts/recolectar-evidencias.sh Crea directorio con archivos
Evidencias generadas ls ~/laboratorio/evidencias/*/ procesos.txt, conexiones.txt
Sudoers aplicado sudo -l Solo comando permitido
